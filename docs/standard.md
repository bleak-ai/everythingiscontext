# Context rules

How context/ is organized, how a save works, and how the tree is
revised. Open it when you save context or change the tree.

Standard: 1.0. context/ is the project's memory. It holds index.md,
system/ (this file, the log, and the checker), packages/ (portable
procedures), and project/ (what this project knows). system/ and
packages/ are portable; the canonical source is the gcontext-framework
repo. This file is the whole standard. There is no other rule file.

## The law: one purpose per folder

Every folder has one purpose. Each entry (file or folder) serves
that purpose. A file may sit beside folders. Every folder has
exactly one index.md. The index states the folder's purpose in 1 or
2 lines above the generated marker, then lists the entries. The list
is generated by sync-index-files.py. The purpose is hand-written.

## Purpose lines

Every file starts with a title, then 1 or 2 lines that say what it
holds and when to open it. This is the purpose line. sync-index-files.py copies
each entry's purpose line into the parent index. For a file, the
source is the first paragraph after the title. For a folder, the
source is the first purpose line of that folder's index.md above the
marker. A missing purpose becomes TODO(describe), reported as a
finding.

## Shape: few files, each one rich

A path is a chain of common denominators. A folder name is what all
its entries share. Each level down is what a smaller group shares.
A file holds all the facts about one subject: what it is, what
happened to it, what it has. A fact lives in exactly one file.

The tree is as small as the content allows. A file is worth opening
when it holds several facts. A folder is worth opening when it holds
several files that share a name. Prefer one rich file over three
thin ones. Prefer a flat folder over a deep one.

The file test. A named thing (a place, a work, a product, a tool, a
method, a service, a person) gets its own file when three or more
facts are about it. Until then, its facts stay in the file of the
subject it belongs to. The name may appear in several facts of that
file; that is fine. When the third fact arrives, the save creates
the file for it. The earlier facts move there at the next revision.

The folder test. Two files that share a name that no folder has yet
form a folder, named after what they share. Every sibling that also
shares that name moves in at the same time. A folder never holds
one file. A folder never names the whole project; project/ already
is the project.

The pair test, for a revision. For every two entries at one level,
name the smallest expression that covers both. Two entries under
one folder always share something; the question is whether it is
smaller than the folder's own name. When it is, and no folder has
that name, that name is a missing folder, and every sibling it
covers moves in. An entry stays loose at a level only when the
smallest expression it shares with every sibling is the folder's
own name. Repeat inside every new folder until every level passes.
Example, in a bakery's context: oven.md and mixer.md share
equipment, sourdough.md and brioche.md share recipes; the bakery
covers all four but is not the smallest expression, so equipment/
and recipes/ are missing folders.

## Save

On every save, at every level, ask: what does this fact share with
what is already here?

1. Go down while a folder names something the fact shares.
2. Find the file of the fact's subject. Add the fact there.
3. When the fact is about a named thing that now has three facts,
   create the file for it (file test). When the new file shares a
   name with a sibling that no folder has, create the folder and
   move both in (folder test) at the same save.
4. When nothing is shared, add the fact to the nearest subject
   file, or start a new file at the root when no subject fits.
5. A correction replaces the wrong line in the file that holds it.
   A duplicate adds nothing.
6. Never ask for approval. Apply, then report the path. The owner
   reviews the git diff.
7. A Stop hook (journal-every-n-turns.py) writes a journal entry every
   ten turns. /add-to-context promotes journal entries into project/.
   The agent also saves at the end of a task.

A save may create files and folders. Only a revision moves what
already exists, apart from the moves in step 3.

## Journal

context/journal/ holds raw facts captured per session. Each session
file stays under the date of its first entry. Each entry starts with
`## Entry N (HH:MM)`. It then has one fact per line. Facts include
decisions, paths, names, numbers, results, and traps. Do not add
narration, routing, or an index sync.

The journal is outside the file test, the folder test, and the pair
test. It is outside the tracker fact count and the index checks.
/add-to-context reviews journal entries and promotes facts into
project/.

## Pointers

A fact that names a second subject with its own file leaves a
pointer line there: `-> <path from project/>: <short id>`.
A pointer is not a fact. Never create a file only for a pointer.

## Names

Name a file after its subject: lowercase, hyphens, no prefix.
the-idiot.md, not known.the-idiot.md. History files (log.md) are
append only. Instruction files are numbered steps.

## Revision

The tree grows one save at a time, so it drifts. The tracker
(track-context-changes.py) shows facts and folders added since the
last structure check after every assistant turn; the owner runs
/check-structure when the count is high; the check appends a
structure check line to log.md. A revision reads every file, applies
the file test, the folder test, and the pair test to the whole tree,
and proposes moves (split a file, merge, split, rename, new parent).
The owner accepts or rejects. On accept, the revision applies the
moves, updates pointer lines, and appends to system/log.md. On
reject, the owner's comment enters the next proposal.

A revision aims at the smallest tree that passes the three tests.
It also merges: two files whose facts are about one subject become
one file, and a file with fewer than three facts folds back into
its parent subject unless it is the only file about a thing the
project tracks on its own (a city, a work, a service).

## Checks

`uv run context/system/scripts/sync-index-files.py --write` regenerates
every index list. `--check` fails on: a folder without index.md, a
name with an uppercase letter, a file without a purpose line, an
index entry that names a missing entry or omits an existing entry,
a TODO(describe) placeholder, and a pointer line whose target file
does not exist. A git pre-commit hook runs --check. If a check
blocks legitimate work, stop and ask; never weaken the check alone.
sync-index-files.py skips context/journal/.

## Rule about rules

No rule without a consumer: every line above is enforced by
sync-index-files.py, track-context-changes.py,
journal-every-n-turns.py, journal-review.py, by a placement step, or
by a revision step. A rule that nothing enforces is deleted.
